# Architecture

## Goals

1. **Colocation** — everything about a feature (server logic, client controllers, UI, shared types) lives in one folder so edits stay localized.
2. **Runtime separation** — at sync time, server code must land in `ServerScriptService` and client code in `StarterPlayerScripts` so Roblox's replication and trust boundaries are correct.

These two goals conflict with Rojo's native model, which maps one filesystem path to one Roblox tree node. The splitter reconciles them.

## Directory map

```
Boil/
├── rokit.toml                  toolchain pins (rojo, wally, lune)
├── wally.toml                  Roblox package deps (React, ReactRoblox, Loader)
├── default.project.json        Rojo sync tree — reads from build/ and src/
├── tools/
│   └── split.luau              the splitter (authoritative build step)
├── src/
│   ├── features/<Name>/        colocated feature code (what you edit)
│   ├── server/init.server.luau global server entry (Script)
│   ├── client/init.client.luau global client entry (LocalScript)
│   └── shared/                 non-feature shared code
│       └── utils/              shared utilities (includes LoadOrdered)
├── build/                      generated by tools/split.luau (gitignored)
│   ├── shared/<Feature>/       → ReplicatedStorage/Features/<Feature>
│   ├── server/<Feature>/       → ServerScriptService/Features/<Feature>
│   └── client/<Feature>/       → StarterPlayerScripts/Features/<Feature>
└── Packages/                   generated by wally install (gitignored)
```

## The split model

Inside `src/features/<Feature>/`, files are named with intent-signalling suffixes:

| Source filename            | Routed to                                                        | Resulting instance                  |
| -------------------------- | ---------------------------------------------------------------- | ----------------------------------- |
| `Something.server.luau`    | `build/server/<Feature>/Something.luau`                          | `ServerScriptService.Features.<Feature>.Something` (ModuleScript) |
| `Something.client.luau`    | `build/client/<Feature>/Something.luau`                          | `StarterPlayerScripts.Features.<Feature>.Something` (ModuleScript) |
| `Something.ui.luau`        | `build/shared/<Feature>/Something.luau`                          | `ReplicatedStorage.Features.<Feature>.Something` (ModuleScript) |
| `init.luau`, `Foo.luau`    | `build/shared/<Feature>/<same-name>`                             | `ReplicatedStorage.Features.<Feature>.*` (ModuleScript) |

Key point: **the `.server` / `.client` / `.ui` suffixes are signals to the splitter, not to Rojo.** The splitter strips them so the outputs are regular ModuleScripts that the entry loaders can `require`.

## Rojo configuration

`default.project.json` points at *both* `src/` (entries and shared code) and `build/` (features):

```json
{
  "ReplicatedStorage": {
    "Packages": { "$path": "Packages" },
    "Shared":   { "$path": "src/shared" },
    "Features": { "$path": "build/shared" }
  },
  "ServerScriptService": {
    "Server":   { "$path": "src/server" },
    "Features": { "$path": "build/server" }
  },
  "StarterPlayer": {
    "StarterPlayerScripts": {
      "Client":   { "$path": "src/client" },
      "Features": { "$path": "build/client" }
    }
  }
}
```

`src/server/init.server.luau` promotes the `Server` node to a `Script` (because Rojo reads `init.*.luau` as the folder itself). Same for `src/client/init.client.luau` → `Client` `LocalScript`. This was chosen over `main.*.luau` because Rojo otherwise creates an ambiguous parent-script node.

## Entry-script flow

### Server (`src/server/init.server.luau`)

```lua
local modules = Loader.LoadDescendants(ServerScriptService:WaitForChild("Features"))
Loader.SpawnAll(LoadOrdered(modules), "Start")
```

1. `Loader.LoadDescendants(root, Loader.MatchesName("Service$"))` walks the Features tree, `require`s only ModuleScripts whose name ends in `Service` (client side uses `Controller$`), and returns the list of returned values. The name filter skips React components, view containers, and other non-startable modules that happen to live under a feature folder.
2. `LoadOrdered` sorts that list by each module's `.Priority` field (ascending; missing = last).
3. `Loader.SpawnAll(list, "Start")` invokes `module.Start()` on each under `task.spawn`, so a slow `Start` doesn't block peers.
4. Then `Loader.LoadDescendants(root, Loader.MatchesName("Command$"))` requires every server-realm presentation (Cmdr commands) for its self-registration side effect — no `Start`.

### Client (`src/client/init.client.luau`)

The client entry **names no content feature** — it discovers everything:

1. **Auto-require every feature** (`Features:GetChildren()`, pcall'd) so each feature's load-time side effects run (the PlayerData / Settings auto-discovery loops). The only feature named explicitly is `UIShell`, whose `FrameProvider` is the structural shell that must wrap the tree.
2. **Discover presentations** — `Loader.LoadDescendants(ClientFeatures, …)` requires every `*Presentation` / `*WorldInteraction` module **before** the root mounts, so they self-register into `UIRegistry` (roots + screen slots). See [presentations.md](game/presentations.md).
3. **Mount** `SkinProvider → FrameProvider → Frame(UIRegistry.getRoots())`. The active skin resolves every `ui.*` primitive (see [skin-contract.md](game/skin-contract.md)).
4. **Load + start controllers** (`Controller$`), then `ReplicaController.RequestData()` once listeners are wired.

Result: adding a feature or a presentation needs **zero edits** to either entry file. See [Adding a Feature](adding-a-feature.md) for the conventions.

## Load ordering

Any feature module can declare a numeric `Priority`:

```lua
local HealthService = {}
HealthService.Priority = 10      -- lower runs earlier; unset = runs last

function HealthService.Start() ... end
return HealthService
```

The sort is stable-ascending via `src/shared/utils/LoadOrdered.luau`. Use this when one service must finish its `Start` before another begins — e.g. a `ConfigService` with `Priority = 1` that downstream services rely on.

If two services have no ordering dependency, leave `Priority` unset and let them run in arbitrary order (fastest; no coupling).

## Why not Rojo's `globIgnorePaths`?

Rojo has project-wide glob ignores but no *per-node* filtering — you can't point three `$path` entries at the same folder and include different files in each. Hence the splitter.
